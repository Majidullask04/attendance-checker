# Deployment Guide — MrElectric Attendance

Full-stack app: **React (Vite) frontend** + **Node/Express API** + **SQLite** on a Render
persistent disk. This guide reflects the codebase **after** the production-readiness fixes
described below.

---

## Verdict: is it deployable now?

**Yes — after you commit the fixes in this repo and do two one-time manual steps** (untrack
`.env`, and register the admin account first). Four real problems that would have broken the
deployment or leaked data have been fixed in code. The remaining steps are operational, not
code changes.

| # | Problem (before) | Status | Consequence if left unfixed |
|---|------------------|--------|-----------------------------|
| 1 | SQLite used a relative path `./database.sqlite` | ✅ Fixed | Silent data loss / DB wiped on restart |
| 2 | Disk mounted **over** the backend source dir (`/opt/render/project/src/backend`) | ✅ Fixed | Mount can hide your code → app fails to boot |
| 3 | CORS allowed exactly one hardcoded URL | ✅ Fixed | Frontend can't reach API → white screen |
| 4 | 6 demo users seeded with `null` passwords; admin locked out | ✅ Fixed | Fake data in prod; admin can never log in |
| 5 | `.env` and the SQLite DB were not git-ignored | ✅ Fixed | Secrets / local config / DB committed to git |

## What changed and why

**`backend/db.js`**
- Database path now comes from `process.env.DB_PATH` (falls back to `./database.sqlite` for
  local dev), and the parent directory is created on startup. On Render this points at the
  persistent disk, so data survives restarts and redeploys.
- **All 6 demo employees were removed.** The database now starts empty. The admin is created
  by *self-registration* (see below), and every other employee registers through the app and
  is approved by the admin — exactly the intended workflow.

**`backend/server.js`**
- CORS now reads `FRONTEND_URL` as a **comma-separated list** of allowed origins, normalizes
  trailing slashes, and allows header-less requests (health checks, curl). You can list more
  than one origin without touching code.
- The HTTPS redirect only fires for traffic known to be HTTP, so Render's internal health
  checks aren't bounced with a 301.

**`render.yaml`**
- Disk now mounts at **`/var/data`** (a dedicated path outside the source tree) instead of on
  top of your code. `DB_PATH=/var/data/database.sqlite`.
- Added `healthCheckPath: /api/health`, a SPA rewrite for the static site, and `plan: starter`
  (persistent disks require a paid instance — see "Cost" below). `JWT_SECRET` is still
  auto-generated by Render.

**`.gitignore`** — now ignores `.env*` (except `.env.example`) and all SQLite files.

## One-time step before you push

Your `.env` file was previously committed. Stop tracking it so the localhost API URL and any
future secrets stay out of git (the file stays on your machine for local dev):

```bash
git rm --cached .env
git commit -am "chore: production-readiness fixes; stop tracking .env"
git push
```

## Deploy on Render (Blueprint)

1. Push this repo to GitHub/GitLab (the `render.yaml` is at the repo root).
2. In the Render dashboard: **New → Blueprint**, and select this repository.
3. Render reads `render.yaml` and creates two services:
   - `mrelectric-attendance-api` (Node web service, with a 1 GB disk)
   - `mrelectric-attendance` (static site)
4. Click **Apply** and wait for both to build. `JWT_SECRET` is generated automatically.

### If the assigned URLs differ from the defaults

Render's `.onrender.com` subdomains are globally unique. If `mrelectric-attendance` or
`mrelectric-attendance-api` is already taken, Render appends a suffix. If that happens:

- Copy the **actual** frontend URL → set the API's `FRONTEND_URL` env var to it → redeploy the API.
- Copy the **actual** API URL → set the static site's `VITE_API_URL` to `<that-url>/api` →
  redeploy the frontend (Vite bakes this in at build time).

`FRONTEND_URL` accepts a comma-separated list, e.g.
`https://mrelectric-attendance.onrender.com,https://attendance.mrelectric.com`.

## Post-deploy checklist

```
□  1. Both services show "Live" in Render
□  2. Visit https://<api-url>/api/health  → {"ok":true,...}
□  3. Open the frontend → no CORS errors in the browser console
□  4. Sign up as admin (ADMIN_EMAIL + your password) → lands on the admin dashboard
□  5. Generate/verify an active QR token from the admin QR manager
□  6. Sign up a test employee (different email) → "pending approval" message
□  7. Approve that employee from the admin approvals screen
□  8. Employee logs in → scans QR → check in → check out
□  9. Redeploy the API once, then confirm the admin + data are still there
       (proves the /var/data disk persists)
```

## Cost & the free alternative

Persistent disks on Render require a **paid instance type** (Starter or higher) — hence
`plan: starter` in `render.yaml`. The static frontend is free. Check Render's current pricing
for exact figures, and note the free instance type does **not** support disks and spins down
when idle.

If you want a zero-cost path, keep the frontend as a static site but replace SQLite with a
hosted database (e.g. Render Postgres, or a SQLite-compatible service like Turso/libSQL) and
drop the `disk` block. That's a larger change and is not applied here.

## Local development

```bash
# Terminal 1 — API (from backend/)
cd backend
npm install
JWT_SECRET=dev-secret ADMIN_EMAIL=mrelectricalworks02@gmail.com npm run dev
#   → http://localhost:3001   (DB_PATH defaults to ./database.sqlite)

# Terminal 2 — frontend (from repo root)
npm install
npm run dev
#   → http://localhost:5173  (VITE_API_URL defaults to http://localhost:3001/api)
```

The API refuses to start without `JWT_SECRET` — that's intentional.
